## Example 1: Meeting Agenda - Sprint Planning

**Input:**
```
Sprint planning for Q2 Platform Migration project. Team of 8 engineers + 1 designer.
Need to finalize API migration roadmap, prioritize technical debt, and resolve database
scaling approach. Attendees: Engineering leads (Alice, Bob), Product Manager (Carol),
Designer (David), and TPM (me).
```

**Output:**
```markdown
# Sprint Planning Meeting - Q2 Platform Migration

## Meeting Objective
Finalize the Q2 Platform Migration roadmap with consensus on API migration sequence,
technical debt priorities, and database scaling strategy to ensure successful sprint execution.

## Attendees & Roles
- **Alice, Bob** (Engineering Leads) - Technical feasibility and effort estimation
- **Carol** (Product Manager) - Business priorities and user impact
- **David** (Designer) - UX implications and design dependencies
- **TPM** (You) - Facilitate, track decisions, manage timeline

## Agenda Items

### 1. API Migration Roadmap Review (25 minutes)
- **Lead:** Engineering Leads
- **Discussion Points:**
  - Which endpoints to migrate first (priority order)
  - Dependencies between endpoints
  - Rollback strategy for each phase
- **Expected Outcome:** Agreed-upon migration sequence with clear phases

### 2. Technical Debt Prioritization (20 minutes)
- **Lead:** Engineering Leads + Product Manager
- **Discussion Points:**
  - Current tech debt backlog review
  - Impact on velocity if not addressed
  - Trade-offs: new features vs. tech debt
- **Expected Outcome:** Top 3 tech debt items for this sprint

### 3. Database Scaling Approach (30 minutes)
- **Lead:** Engineering Leads
- **Discussion Points:**
  - Options: Vertical scaling vs. Horizontal sharding vs. Read replicas
  - Cost implications of each approach
  - Timeline to implement
  - Risk mitigation strategies
- **Expected Outcome:** Decision on scaling approach with implementation plan

### 4. Sprint Capacity & Assignment (15 minutes)
- **Lead:** TPM + Engineering Leads
- **Discussion Points:**
  - Team capacity for this sprint (accounting for PTO, on-call)
  - Story point allocation across API migration + tech debt
  - Owner assignment for each workstream
- **Expected Outcome:** Committed sprint backlog with clear owners

## Pre-Work
- **Alice & Bob:** Review API dependency map, prepare scaling options analysis
- **Carol:** Prioritize tech debt items by business impact
- **David:** Flag any design dependencies for API changes
- **TPM:** Circulate this agenda 24 hours before meeting

## Success Criteria
- ✅ Unanimous agreement on migration sequence
- ✅ Top 3 tech debt items identified and committed
- ✅ Database scaling decision made with clear next steps
- ✅ Sprint backlog finalized with no ambiguity on ownership

**Duration:** 90 minutes
**Location:** Conference Room A / Zoom Link
**Follow-up:** TPM to send meeting notes and action items within 2 hours
```

## Example 2: Thread Summary - Database Decision

**Input:**
```
Alice (10:23 AM): Team, we need to finalize the database solution for the new analytics feature.
Current proposal is PostgreSQL.

Bob (10:25 AM): I think PostgreSQL makes sense given our existing stack. We already have expertise.

Carol (10:27 AM): What about MongoDB? We discussed document storage benefits last quarter for this use case.

Bob (10:30 AM): True, MongoDB could work. But we'd need to onboard the team on MongoDB best practices.
That's 2-3 weeks of ramp-up time.

Alice (10:32 AM): Timeline is tight - we need to ship by end of Q1. Can we afford 3 weeks of learning curve?

David (10:35 AM): Also, our DevOps pipeline is optimized for Postgres. Adding Mongo means new backup
strategies, monitoring dashboards, etc.

Carol (10:38 AM): Fair points. I withdraw the Mongo suggestion. Let's go with Postgres.

Alice (10:40 AM): Great. Decision made: PostgreSQL it is. Carol, can you document this decision
in the design doc with the rationale?

Carol (10:41 AM): Yes, I'll update the design doc by end of day Friday.

Bob (10:42 AM): I'll start the schema design. Will share draft by Wednesday for feedback.

Alice (10:43 AM): Perfect. Thanks everyone!
```

**Output:**
```markdown
# Thread Summary: Database Selection for Analytics Feature

## TLDR
Team selected PostgreSQL over MongoDB for the new analytics feature based on existing expertise,
tight timeline, and DevOps infrastructure compatibility. Decision documented and schema design in progress.

## Key Decisions Made
1. **Database choice: PostgreSQL** (not MongoDB)
   - Rationale: Team expertise, timeline constraints (Q1 deadline), existing DevOps pipeline
   - MongoDB would require 2-3 weeks onboarding + new backup/monitoring infrastructure

## Action Items
- [ ] **Carol**: Document database decision and rationale in design doc (Due: Friday EOD)
- [ ] **Bob**: Create schema design draft and share for team feedback (Due: Wednesday)

## Open Questions / Blockers
None - decision finalized, team aligned.

## Context for Future Reference
- **Timeline pressure:** Need to ship by end of Q1
- **Technical consideration:** DevOps pipeline currently optimized for Postgres only
- **Alternative considered:** MongoDB was discussed but rejected due to learning curve and infrastructure overhead
- **Team consensus:** Unanimous agreement on PostgreSQL after discussing trade-offs
```

## Example 4: Risk Analysis - Auth System Migration

**Input:**
```
Migrating 500K users from legacy authentication system to new OAuth2 implementation.
Timeline: 3 months (Jan - March 2024)
Team: 5 backend engineers, 1 SRE, 1 QA
Integration with 12 downstream services (mobile apps, web app, admin portal, 3rd party integrations)
Must maintain 99.9% uptime during migration
Legacy system is 5 years old with minimal documentation
```

**Output:**
```markdown
# Risk Analysis: OAuth2 Authentication System Migration

## Technical Risks

### Risk 1: Data Migration Integrity
- **Risk:** User credentials and session data corruption during migration from legacy system to OAuth2
- **Probability:** Medium
- **Impact:** High (user lockouts, data loss, security vulnerabilities)
- **Mitigation:**
  - Implement dual-write strategy during migration period
  - Build comprehensive data validation checks pre/post migration
  - Run migration on 1% user cohort first, validate, then scale
  - Maintain rollback capability for 2 weeks post-migration
- **Owner:** Backend Lead
- **Timeline:** Implement dual-write in Week 1, validation framework in Week 2

### Risk 2: Downstream Service Integration Failures
- **Risk:** 12 downstream services may have incompatible OAuth2 implementations or break during cutover
- **Probability:** High
- **Impact:** High (service outages, broken user flows)
- **Mitigation:**
  - Audit all 12 services' auth implementations (Week 1-2)
  - Create integration test suite covering all service combinations
  - Phased rollout per service (mobile first, then web, then admin, then 3rd party)
  - Maintain legacy auth support for 30 days post-launch (dual-mode operation)
- **Owner:** SRE + Integration Team Leads
- **Timeline:** Complete audit by Week 3, test suite by Week 4

### Risk 3: Legacy System Undocumented Behavior
- **Risk:** 5-year-old system has tribal knowledge and undocumented edge cases that break in new system
- **Probability:** High
- **Impact:** Medium (unexpected bugs, user experience degradation)
- **Mitigation:**
  - Interview original engineers (if available) to document tribal knowledge
  - Analyze production logs for edge case patterns
  - Build shadow mode where new auth runs in parallel for 2 weeks before cutover
  - Extensive beta testing with power users who might hit edge cases
- **Owner:** Tech Lead + QA
- **Timeline:** Knowledge transfer sessions Week 1-2, shadow mode Week 8-10

### Risk 4: Performance Degradation Under Load
- **Risk:** New OAuth2 system may not scale to 500K users, especially during peak traffic
- **Probability:** Medium
- **Impact:** High (system outages, SLA breaches, user frustration)
- **Mitigation:**
  - Load testing at 2x expected peak capacity (Week 5-6)
  - Gradual rollout: 1% → 10% → 50% → 100% over 4 weeks
  - Auto-scaling configured with conservative thresholds
  - Circuit breakers to fall back to legacy system if OAuth2 latency spikes
- **Owner:** SRE
- **Timeline:** Load testing complete by Week 6, rollout strategy defined Week 7

## Schedule Risks

### Risk 5: 3-Month Timeline Underestimation
- **Risk:** Complex migration may take longer than 3 months, especially with unknown unknowns
- **Probability:** Medium
- **Impact:** Medium (delayed launch, opportunity cost)
- **Mitigation:**
  - Build 2-week buffer into schedule (target Feb 15 internally, commit March 1 externally)
  - Identify scope cutbacks if timeline slips (defer 3rd party integrations to Phase 2)
  - Weekly risk reviews to surface delays early
  - Pre-commit engineering resources for March in case of overflow
- **Owner:** TPM
- **Timeline:** Ongoing weekly reviews

### Risk 6: Dependency on External OAuth Provider
- **Risk:** If using external provider (Auth0, Okta), vendor delays or outages block progress
- **Probability:** Low
- **Impact:** High (complete project blocker)
- **Mitigation:**
  - Select vendor with strong SLA (99.99% uptime)
  - Build against vendor's staging environment first
  - Have migration plan to self-hosted OAuth if vendor fails
  - Contractual guarantees on support response times
- **Owner:** Engineering Director + Procurement
- **Timeline:** Vendor selection and contracting by Week 1

## Resource Risks

### Risk 7: Team Capacity Constraints
- **Risk:** Team of 6 engineers may be insufficient for 3-month timeline, especially with production support
- **Probability:** Medium
- **Impact:** Medium (timeline slip, quality issues)
- **Mitigation:**
  - Dedicate 4 engineers full-time, 2 split with production support (80/20)
  - Identify 2 backup engineers who can ramp up if needed
  - Reduce meeting overhead during migration (no non-essential meetings)
  - Defer new feature work to other teams during critical migration periods
- **Owner:** Engineering Manager
- **Timeline:** Resource allocation finalized Week 1

### Risk 8: Key Engineer Attrition
- **Risk:** Loss of key engineer (especially legacy system expert) during migration
- **Probability:** Low
- **Impact:** High (knowledge loss, timeline slip)
- **Mitigation:**
  - Cross-train at least 2 engineers on legacy system (documentation sprint Week 1)
  - Pair programming on critical migration components
  - Retention bonuses for team (if budget allows)
  - Maintain good morale (celebrate milestones, avoid burnout)
- **Owner:** Engineering Manager + HR
- **Timeline:** Documentation complete Week 2, retention plan Week 1

## Dependency Risks

### Risk 9: Mobile App Release Cycles
- **Risk:** Mobile apps have 1-2 week app store review cycles, delaying OAuth2 rollout
- **Probability:** Medium
- **Impact:** Medium (delayed mobile auth migration)
- **Mitigation:**
  - Submit mobile updates 2 weeks before planned auth cutover
  - Implement feature flags to enable OAuth2 remotely after app approval
  - Maintain backward compatibility so old app versions still work
  - Prepare expedited review request if needed (Apple/Google emergency process)
- **Owner:** Mobile Lead
- **Timeline:** Submit apps Week 10 (for Week 12 launch)

### Risk 10: Security Audit Delays
- **Risk:** Security team audit of OAuth2 implementation reveals issues that require rework
- **Probability:** Medium
- **Impact:** Medium (timeline slip, scope increase)
- **Mitigation:**
  - Involve security team early (Week 2 design review)
  - Follow OWASP OAuth2 best practices from day 1
  - Schedule security audit at Week 8 (4 weeks before launch for fix time)
  - Pre-audit with external security consultant to catch issues early
- **Owner:** Security Lead + Engineering Lead
- **Timeline:** Design review Week 2, audit Week 8

## Risk Summary Matrix

**Top 5 Risks by Priority (Probability × Impact):**

1. **Downstream Service Integration Failures** (High × High = Critical)
   - Mitigation: Phased rollout per service, dual-mode operation

2. **Legacy System Undocumented Behavior** (High × Medium = High)
   - Mitigation: Shadow mode, knowledge transfer, extensive beta testing

3. **Performance Degradation Under Load** (Medium × High = High)
   - Mitigation: Load testing, gradual rollout, circuit breakers

4. **Data Migration Integrity** (Medium × High = High)
   - Mitigation: Dual-write, validation checks, 1% pilot

5. **3-Month Timeline Underestimation** (Medium × Medium = Medium)
   - Mitigation: 2-week buffer, scope cutback plan, weekly reviews

**Recommended Actions:**
1. Start downstream service audit immediately (Risk #1)
2. Implement shadow mode for legacy system observation (Risk #2)
3. Schedule load testing for Week 5-6 (Risk #3)
4. Engage security team in Week 2 design review (Risk #10)
5. Document and cross-train on legacy system Week 1-2 (Risk #8)
```

## Example 5: Project Charter

**Input:**
```
Build a real-time notification system for our mobile and web apps.
Business goal: Increase user engagement by 25% through timely notifications.
Target: 10M users, support 50K notifications per second.
Timeline: 6 months (Q1-Q2 2024)
Team: 2 backend engineers, 1 mobile engineer, 1 web engineer, 1 QA, 1 TPM
Tech stack: WebSockets, Redis, PostgreSQL, AWS infrastructure
Key stakeholders: VP Product, Engineering Director, Mobile team lead, Growth PM
```

```markdown
**VP Product** (Accountable for business outcomes)

and support growth initiatives through targeted messaging.

**Why this matters:** Notifications are proven to increase engagement by 20-30% in similar products.
Our current email-only approach has 15% open rates; push notifications typically see 50%+ engagement.

1. **Increase user engagement by 25%** (measured by DAU/MAU ratio)
2. **Reduce churn by 10%** through re-engagement notifications
3. **Enable growth team to run notification experiments** (A/B testing framework)
4. **Support 10M users** with sub-second delivery latency
5. **Align with company OKR:** "Improve user retention and activation"

**Success Metric:** 25% increase in DAU/MAU within 3 months of launch

**At Launch (End of Q2):**
- ✅ System handles 50K notifications/second (peak capacity)

- ✅ **25% engagement increase** (primary success metric)

### In Scope
**Phase 1 (Q1 - Months 1-3):**
- Real-time notification infrastructure (WebSockets, Redis, PostgreSQL)
- iOS and Android push notifications (via FCM/APNS)
- Web browser notifications
- Basic notification types: transactional, promotional, system alerts
- User preferences (opt-in/out, notification settings)
- Admin dashboard for manual notification sending
- Analytics dashboard (delivery rates, open rates, conversions)

**Phase 2 (Q2 - Months 4-6):**
- A/B testing framework

The following are explicitly NOT included to prevent scope creep:

- ❌ Email notifications (existing system handles this)
- ❌ SMS notifications (different infrastructure, separate project)

- ❌ Notification localization (English only for MVP, i18n in Phase 3)
- ❌ Desktop apps (no desktop app exists yet)
```
